# Ministry portal integration contract (proposal)

This is a deployment contract for review, not evidence of ministry certification. Southern Passage is currently a research prototype: SIC forecasting and observation sampling are not validated route-safety decisions.

## Deliverable and portal wiring

The same application container now serves the browser workspace at `/portal/` and the versioned API at `/api/v1/`. `/portal` redirects to `/portal/`; the trailing slash is necessary for relative CSS and JavaScript assets. Only six named browser assets are served, not the application directory, datasets, model artifacts, or reports. The browser uses the current origin for API calls on a non-localhost ministry host. The gateway must expose both paths on one approved HTTPS origin and protect **both** paths with its OIDC session. It must authorize the browser's `/api/v1/*` calls and inject the private service bearer only on the gateway-to-application hop; no bearer belongs in browser JavaScript or a cookie.

### SSO identity and role boundary

The application does **not** know the ministry's identity-provider URL, client registration, group directory, or assignment policy. It does not perform a browser login. Instead, an approved gateway validates the ministry's OIDC session and maps current groups to these application roles: `analyst`, `science_reviewer`, `maritime_reviewer`, `security_reviewer`, `operations_reviewer`, `release_authority`, and `auditor`. Before forwarding a review-workflow request, the gateway must strip any user-supplied `X-SP-Actor-Assertion` and `X-Request-ID`, issue a new request ID, inject the private workload bearer, and attach a newly signed internal assertion. No browser may see the assertion or workload secret. This follows the signed internal-identity propagation pattern; the internal assertion is **not** an OIDC ID token.

The `X-SP-Actor-Assertion` wire format is `base64url(canonical_payload).base64url(HMAC_SHA256(secret, encoded_payload))`, with no Base64 padding. `canonical_payload` is UTF-8 JSON serialized with lexicographically sorted keys, no whitespace separators, and no NaN. Required fields: `iss` (configured internal gateway issuer), `aud` (`southern-passage-review` unless configured otherwise), `sub` (stable non-reassigned user identifier scoped to issuer), `roles` (array of mapped application roles), integer Unix `iat` and `exp`, exact HTTP `method`, exact internal request `path`, and the gateway-generated `request_id`. The service requires `iat` no more than 5 minutes old, `exp` in the future and within 5 minutes of issue, and accepts at most 30 seconds of clock skew. Gateway clocks and key rotation must be governed. Use an independently generated secret of at least 32 characters from the approved secret manager, not the workload bearer or a user password. In production restrict the API network to the gateway; the assertion is not a substitute for TLS, gateway authorization, or the service bearer.

Set `SOUTHERN_PASSAGE_REVIEW_ENABLED=true`, `SOUTHERN_PASSAGE_REVIEW_ASSERTION_ISSUER`, `SOUTHERN_PASSAGE_REVIEW_ASSERTION_AUDIENCE`, and `SOUTHERN_PASSAGE_REVIEW_DB` only after that gateway is ready. Supply the shared secret by either `SOUTHERN_PASSAGE_REVIEW_ASSERTION_SECRET_FILE` (preferred: a readable secret-manager mount) or `SOUTHERN_PASSAGE_REVIEW_ASSERTION_SECRET`, never both. The review API fails closed while disabled and refuses startup if enabled without the assertion secret or issuer. The provided Compose file uses a writable persistent volume solely for `/app/state/reviews.sqlite3`; observation/model mounts remain read-only. Back up, encrypt, restrict, and test restore of this volume. For multi-replica or higher-volume production, migrate the ledger to a ministry-approved transactional database; this SQLite reference deployment is single-site and does not establish distributed HA.

### Independent review gates

An `analyst` files a case from an observed route review. Filing recomputes the source-backed packet, requires its source hash to match what the analyst saw, checks its digest, and freezes the packet. Four separate people with the science, maritime, security, and operations roles each record one immutable gate decision (`reviewed`, `blocked`, or `changes_required`) with rationale; affirmative attestations require a document-management record ID and file SHA-256. The creator cannot review the case, and one person cannot sign multiple gates. A blocked/changes-required case closes and requires a new case. Only when all four gates say `reviewed` may a fifth independent `release_authority` record `package` with an evidence reference. The terminal state is `pilot_review_packaged`, **not** operational clearance.

The review store is append-only through the API, with event hashes chained to the frozen packet hash and verified when cases are read. Its SQLite file is not an immutable or digitally signed audit repository: a database administrator can replace it. The ministry must replicate events or hash-chain heads to an approved append-only audit destination, verify cited document hashes against the document-management system, define retention and correction procedures, and control backup/restore. Current endpoints do not upload or authenticate external evidence files, nor do they establish whether a reviewer was professionally authorized. The gateway's role assignment and the ministry's evidence-policy owner must supply those controls.

Suggested gateway route mapping (replace the host and path according to the ministry's portal standard):

```text
https://<approved-portal-host>/southern-passage/  → internal /portal/
https://<approved-portal-host>/api/v1/            → internal /api/v1/
```

If the gateway publishes the UI at a subpath, it must rewrite `/portal/` relative assets consistently. A dedicated portal subdomain with `/portal/` and `/api/v1/` on the same origin is the simplest supported mapping. A different API path or origin needs a gateway-side rewrite or a vetted build-time configuration; do not inject a secret or use a browser-accessible private upstream address. Google Fonts are currently fetched from public Google domains; an isolated ministry network should self-host approved font files or accept the system-font fallback after an asset/CSP review.

### Machine contract and review workflow

- `GET /api/v1/integration/capabilities` describes the available v1 workflows and explicitly reports that navigation clearance is unavailable.
- `GET /api/v1/integration/openapi.json` returns the API contract behind the service credential even when public Swagger/ReDoc are disabled in production.
- `GET /api/v1/integration/status` gives component-level research availability, source-monitor state, evidence identifiers, and an explicit `operational_decision_ready: false`. It is a status display, not a safety or scientific readiness gate. The response may calculate a checksum of the mounted historical iceberg archive, so poll it at a modest interval.
- `POST /api/v1/reviews/route` accepts the same bounded, validated request as observed route exposure. It returns a v1 JSON packet containing input geometry, dated observation provenance, sampled SIC/coverage, a stable `analysis_key`, generated `packet_id`, request ID, and an unsigned SHA-256 digest. The digest covers canonical sorted JSON of the packet *without* `integrity`; it detects accidental changes but does not authenticate who issued it. The packet's decision remains null and its status is `awaiting_human_review`.
- `POST /api/v1/route/exposure` also returns a descriptive evidence gate. It abstains from a navigation decision even when observation coverage passes a 90% **research-display** threshold, because forecast uncertainty, cross-sensor agreement, vessel authorization, and hazard checks are absent. Its `ice_edge_fragility` identifies 5-km sections whose mean observed SIC crosses the 15% ice-edge reference under a hypothetical ±5-percentage-point change; this is not a calibrated interval. An optional `research_vessel_profile` compares observed maximum SIC and coverage with caller-entered limits but never authenticates a Polar Water Operational Manual or grants clearance.
- `POST /api/v1/route/candidates` additionally returns `fixed_path_counterfactuals`: the three existing observed-grid alternatives are each re-scored under uniform −5, 0, and +5 percentage-point SIC changes with the **same** distance-plus-ice objective. A changed preferred fixed alternative exposes sensitivity of this exploratory comparison; candidate geometries are not recomputed, the perturbation is not a forecast distribution, and no vessel route recommendation follows.
- `POST /api/v1/reviews/route/bundle` generates the unsigned JSON packet and RFC 7946 GeoJSON feature from **one** analysis, binding both to the same packet ID and digest. `/api/v1/reviews/route.geojson` provides a standalone GeoJSON feature. These are portable GIS exports, not OGC API-EDR conformance or an authoritative ministry record. The browser downloads the paired outputs from one cached bundle after confirming the source hash still matches the reviewed scene.
- `/api/v1/review-workflow/*` provides the separate SSO-gated case ledger: capabilities, current actor, bounded case list/detail, case filing, and append-only gate decisions. It is disabled until the gateway assertion and writable store are configured. The browser's Review governance panel mirrors that state instead of inventing a local login.
- The browser lets the analyst download that packet or file it into the separate internal review ledger. The ministry's authoritative record service, if adopted, must verify and sign or attest the packet, bind it to the authenticated actor, store it under approved retention, and add a separate operational decision. The present app records process attestations but has no write-back of an authoritative ministry decision or navigation clearance.

### Deployment handoff

### Controlled observation refresh and frozen corridor scorecard

`ml/refresh_viirs.py` stages a new NOAA VIIRS regional subset under a unique run ID, verifies the complete manifest, file sizes/SHA-256, a consistent EPSG:3976 grid, SIC range, dates, pixel availability, and the policy's explicit freshness limits, then atomically switches `active.json`. A rejected run leaves the previous pointer unchanged. `GET /api/v1/observations/active/status` rechecks the local archive and its age on every request, so a previously accepted scene becomes unavailable when stale or tampered with. The checked-in `config/viirs-research-policy.example.json` is **only a research example**; source precedence and thresholds are not ministry-approved. The refresh job must run in a scheduler/isolated ingestion worker with writable data storage; the API mounts that storage read-only. A failed job must alert the data owner, retain its rejection report, and must never silently promote an alternate sensor.

`ml/evaluate_route_corridors.py` scores the frozen `config/research-corridors-antarctic-peninsula.json` transects against previous-day persistence on identical valid points. The output at `outputs/viirs-2024-frozen-corridor-evaluation.json` is served by `GET /api/v1/evaluations/frozen-corridors`. The June–August 2024 result has only 6.8–9.9% common three-day coverage across the three transects; its gate is therefore `insufficient_evidence` despite small numerical model gains on observed points. Transect samples are spatially correlated and are not independent vessel journeys. This does not establish model usefulness for routing. Before an operational pilot, secure denser independent labels, freeze region/season/route definitions in advance, add uncertainty and vessel outcomes, and obtain formal science/maritime acceptance criteria.

The separate `GET /api/v1/evaluations/multiplatform-corridors` exposes the checksum-pinned June–August 2024 S-NPP/NOAA-21/NOAA-20 research comparison. It counts missing days against all 90 scheduled one-day target dates instead of only observed three-day windows. All nine platform–transect coverage gates fail; NOAA-21 reaches only 15.5–17.1% calendar point-day coverage. This is a cross-product diagnostic, not three independent vessel trials, and does not change `operational_decision_ready: false`.

Example local research refresh (requires live NOAA access, not performed by the API container):

```powershell
python ml/refresh_viirs.py --policy config/viirs-research-policy.example.json --root work/active-viirs
python ml/refresh_viirs.py --policy config/viirs-research-policy.example.json --root work/active-viirs --status-only
```

Schedule the first command externally only after the data owner approves a revised policy. Give that worker an exclusive lock, bounded runtime, network egress only to NOAA, a disk quota/retention policy, alerting on nonzero exits, and a monitored backup. The API service must not receive write access to the ingest directory. The example Compose configuration mounts `work/active-viirs` read-only but does not provide a scheduler, backup, alerting, or multi-node HA.

1. Build the pinned image from the repository and scan its dependencies and container against ministry policy. Keep the model and output artifacts pinned to a reviewed image digest.
2. Mount observation and iceberg archives read-only with their manifests. Provide `SOUTHERN_PASSAGE_API_TOKEN` from the approved secret manager and set `APP_ENV=production` plus exact HTTPS `CORS_ORIGINS`. The application refuses production startup with a missing/short token or wildcard/localhost CORS.

6. Obtain the security, science, maritime-safety, and operations approvals below before any operational pilot. Packaging and API integration alone do not make the outputs decision-ready.

## Request path and identity

Recommended production flow:

```text
Browser ── HTTPS/OIDC session ──> Ministry gateway ── private network ──> Southern Passage API
                                      │                                  │
                                      └── actor audit + request ID <─────┘
```

- Serve the browser and API behind the same ministry TLS origin where possible. The gateway validates the OIDC session, maps current ministry roles/permissions to each method and path, and rejects unauthorized actions before forwarding.
- Treat the API bearer as a workload credential only. Store and rotate it in an approved secret manager; inject it server-to-server. It must never reach browser JavaScript, browser storage, a public config endpoint, or application logs.
- The gateway strips any incoming `Authorization`, `X-Request-ID`, and identity/role headers before applying its own authorization decision. It generates a fresh, syntactically safe request ID and forwards that ID plus its service credential. The application echoes `X-Request-ID`; a supplied ID is correlation metadata only and never proof of user identity.
- Do not expose the container directly to the internet or to general ministry user networks. Restrict its ingress to the gateway and explicitly approved operational probes. Keep `/healthz` and `/readyz` internal.
- Enforce TLS, OIDC session validation, role-to-route authorization, CSRF policy for cookie-authenticated browser paths, request-rate limits, request-body size limits, timeouts, and security headers at the gateway. Browser CORS is not an identity control.
- The API independently rejects `/api/*` `POST`/`PUT`/`PATCH` bodies larger than 16 MiB, including chunked bodies without a declared `Content-Length`, before JSON/model parsing. Keep a gateway limit as well (preferably lower and endpoint-specific); the service cap is a last-resort memory bound, not a substitute for edge controls.

## Audit, privacy, and traceability

The API writes one JSON access event for each `/api/*` request with `request_id`, method, path, status code, and duration. It deliberately excludes authorization headers, request bodies, query strings, and route coordinates. Forecast output carries a UUID run ID, coefficient fingerprint, full-artifact SHA-256, an explicit `decision_status: research_only`, the artifact's actual same-product holdout scope/scores against persistence, and limitations. The run evidence says that its inputs are caller-supplied, no calibrated uncertainty is produced, and no independent or operational validation is established; consumers must preserve these fields with the raster rather than treating the SIC output alone as a decision product. The API rejects artifacts whose full-artifact digest does not match their contents; the coefficient fingerprint remains the stable key for evaluation-report matching.

The application event is not actor-attributed, immutable, or a replacement for the gateway audit log. The gateway must persist the authenticated subject/role decision, request ID, upstream status, and (when a forecast was produced) the returned run ID/model fingerprint to the ministry-approved append-only audit destination, under approved retention and access controls. Never infer the actor from a caller-supplied header. Do not copy sensitive voyage geometry into generic access logs; if the ministry needs a record of submitted routes, define a separate access-controlled record and retention policy.

## Data and decision boundary

- The current forecast endpoint accepts caller-supplied gridded SIC inputs; the API cannot authenticate their provenance. A production ingestion path must verify upstream provider, product/version, timestamps, QA flags, CRS/grid, freshness, and checksums before data can be marked authoritative.
- The research-only `GET /api/v1/observations/sic/{date}/forecast` path derives a one-day estimate from two mounted, manifest-checksummed VIIRS scenes, but its model is still only a low-skill research baseline. Its two inputs must be consecutive and identical in product/platform/grid and its response carries both source-file hashes. It enforces a 10% common-pixel display floor that is only a demo placeholder, not an operational data-quality threshold or a guarantee of spatial coverage. The endpoint still lacks operational freshness approval, calibrated uncertainty, independent operational validation, and vessel-specific constraints.
- `GET /api/v1/icebergs/observed-tracks` provides source-measured historical BYU/NIC tracks from a manifest-checksummed archive, and refuses dates after the landing page's published 2025-04-22 endpoint pending source clarification. The archive covers selected large tracked bergs, not a live or complete obstacle feed. It is not wired into route scoring and must not be interpreted as current position, predicted drift, encounter probability, or clearance.
- Missing, stale, malformed, unverified, or unsupported input must produce an explicit unavailable/error state, not a green/passable-route status. API readiness means the research model artifact loaded; it does not mean operational data are fresh or the model is safe for use.
- The browser's newest-scene age label is informational only. Its 48-hour/7-day categories are unapproved demonstration thresholds and must not be used as operational limits; the responsible science/data owner must define product- and mission-specific freshness, coverage, and fallback criteria.
- The NOAA regional VIIRS query last returned September 21, 2026 data when checked on September 30 (about nine days old, although the catalog describes a 12-24-hour NRT latency). The app reports mounted-data age as stale. A bounded NOAA-20 South-polar daily SIC subset is downloaded, checksummed, mounted, and evaluated; this verifies the research ingestion path only. The new refresh worker applies an explicit **example research-only** priority across allowlisted products, but the service does not implement ministry-approved operational source precedence, blending, or failover. Before any pilot, the ministry must approve replacement products, priority, latency limits, QA, and test behavior during source gaps.
- `ml/check_polarwatch_viirs.py` and `GET /api/v1/observations/sic/source-status` provide a low-bandwidth upstream catalog metadata check independent of local NetCDF checksums. The snapshot expires after 24 hours by a demonstration threshold. Production operations must schedule the checker, alert on unavailable/stale results, protect and monitor the snapshot's provenance, and set product-specific freshness/latency limits; this helper is not a scheduler, notification service, signed feed, or automatic ingestion/failover system.
- The observed route-exposure endpoint samples one observed VIIRS field along a line and, by default, a fixed-width 5-km-per-side context swath (configurable 0–20 km per side). That swath is analytical context, not a vessel-specific navigation corridor or clearance. It is not a forecast, route optimizer, bathymetry check, icebreaker-capability assessment, or navigability determination.
- Keep human review and an unmistakable research-only warning. Do not expose model output as a clearance decision or automate vessel routing.

## Pre-pilot acceptance gates

1. Ministry security architecture approves the identity provider, authorization matrix, network boundary, secrets, log destination, retention, incident response, and vulnerability/license review.
2. A named Antarctic sea-ice scientific owner approves dataset versions, QA policy, freshness thresholds, spatial/temporal coverage behavior, and independent regional/seasonal/route-corridor validation.
3. Maritime-safety owners define vessel-specific hazards and thresholds, fallback procedures, human sign-off, and liability boundaries; the current prototype supplies none of these.
4. Operations establish monitoring/alerts, backup and recovery, deployment rollback, model/data lineage, and service-level targets. `/readyz` alone is insufficient.
5. End-to-end staging tests prove browser identity, role denial, secret non-disclosure, audit correlation, stale/missing-data fail-closed behavior, and external ingress restrictions.

Until those gates have owners and verified evidence, the service is a research demonstrator and must not be used to make or automate navigation decisions.
